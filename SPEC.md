# mxsd

mxsd is an XML Schema (XSD) compiler and lightweight XML validation
runtime designed for embedded C applications.

## Architecture

mxsd consists of:

1. `mxsdc`
   Host-side XSD compiler.

2. `libmxsd`
   Portable C validation runtime.

3. Generated C code
   Schema-specific validation code generated by `mxsdc`.

XSD files MUST NOT be parsed on the embedded target.

The target MUST NOT require an XSD parser.

## Compiler

Usage:

    mxsdc schema.xsd -o generated/

Input:

    schema.xsd

Output:

    generated/schema.mxsd.c
    generated/schema.mxsd.h

Generated code MUST be valid C.

## Target API

Typical usage:

    #include "schema.mxsd.h"

    mxsd_result_t result =
        schema_validate(xml);

The generated validator MUST NOT perform dynamic schema parsing.

## XML backend

Initial backend:

    Mini-XML

The public generated API MUST NOT expose internal XSD compiler
representations.

The architecture MUST permit a future streaming/SAX backend.

Recognize:

- xs:annotation

Unknown XSD constructs MUST remain fatal.


## v0.12 — Streaming validator

Add an event-driven validation API independent from Mini-XML DOM.

Example events:

    mxsd_start_element(...)
    mxsd_attribute(...)
    mxsd_text(...)
    mxsd_end_element(...)

Provide a Mini-XML adapter.

The generated schema representation MUST work with both:

- DOM validation
- streaming validation

The streaming validator MUST NOT require storage proportional to the XML
document size.


## v0.13 — Resource-constrained operation

Add configurable limits:

- maximum XML depth
- maximum schema complexity
- maximum attributes
- maximum identity values
- maximum text value length

Support custom allocators.

Provide an option for zero-heap validation when the schema does not require
features needing dynamic storage.

Measure:

- generated code size
- libmxsd flash size
- static RAM
- peak stack
- peak heap

Provide measurements for native_sim and at least one Cortex-M target.


## v0.14 — Conformance

Integrate an appropriately licensed XSD 1.0 conformance test suite.

Generate a machine-readable support report:

    supported
    unsupported
    expected-failure
    passed
    failed

Do not mark a feature supported solely because mxsdc accepts it.

A feature is supported only when positive AND negative conformance tests
pass.


## v0.15 — Reusable declaration groups

Implement:

- `xs:group` definitions and references
- `xs:attributeGroup` definitions and references
- global `xs:attribute` references
- occurrence constraints on model-group references
- circular group-reference detection

Group expansion MUST preserve namespace context and MUST remain bounded by the
configured schema-complexity and runtime descriptor limits.


## v0.16 — Mixed content and anyType

Implement:

- mixed complex content
- the built-in `xs:anyType`
- implicit `xs:anyType` for untyped element declarations
- restrictions and runtime `xsi:type` derivation from `xs:anyType`
- DOM and streaming validation of interleaved character data

Arbitrary content MUST use the existing bounded wildcard machinery and MUST
NOT cause character data to be retained in proportion to the input size.

## v0.17 — Recursive complex types

Implement:

- direct recursion through local element declarations
- mutual recursion between named complex types
- deterministic C descriptor cycles through forward declarations
- DOM and streaming validation bounded by `MXSD_MAX_DEPTH`
- explicit rejection of recursive simple types and circular type derivation

Recursive descriptors MUST NOT cause unbounded schema traversal or allocation.
The first instance element beyond `MXSD_MAX_DEPTH` MUST fail with
`MXSD_ERR_EXCESSIVE_NESTING`.

## v0.18 — Complete XSD regular expressions

Implement the complete XML Schema 1.0 regular-expression grammar:

- grouping, alternation, empty branches, and every repetition form
- positive and negative character classes, ranges, and class subtraction
- single-character, multi-character, XML name, category, and block escapes
- UTF-8 matching by Unicode scalar value using Unicode 16 categories and blocks
- disjunction of sibling pattern facets and conjunction across restriction steps
- implicit whole-value anchoring

The target matcher MUST remain allocation-free and deterministically bounded by
`MXSD_MAX_TEXT_LENGTH`, `MXSD_MAX_PATTERN_LENGTH`, `MXSD_MAX_REGEX_NODES`, and
`MXSD_MAX_REGEX_DEPTH`. Invalid expressions and unknown Unicode properties MUST
fail during schema compilation.

## v0.19 — Notation declarations

Implement:

- global ``xs:notation`` declarations across composed schemas
- public and system identifier metadata in generated descriptors
- the XSD rule that ``xs:NOTATION`` is used only through a restriction with at
  least one enumeration facet
- namespace-aware QName resolution for NOTATION enumeration values
- compile-time rejection of duplicate declarations, invalid identifiers, and
  enumeration values that do not name a declared notation

Runtime NOTATION validation MUST resolve the instance QName by namespace URI
and local name, independently of the lexical prefix.

## v0.20 — Typed data bindings

Implement, behind the opt-in `mxsdc --bindings` option:

- generated C structures for complex types reachable from global elements
- native C types for boolean and fixed-width integer types
- C enumerations for string-derived enumerations
- normalized lexical text for every other simple type
- explicit presence flags, `NULL` pointers, and pointer/count arrays for
  optional and repeated items
- pointers for recursive structures
- a reader that validates first, then fills a structure from a caller-provided
  arena without heap allocation
- a writer that streams to a caller-provided sink, rejects structural errors,
  and can validate while writing

The validator output MUST remain byte-identical with and without
`--bindings`. Constructs that a structure cannot represent faithfully MUST
make binding generation fail; they MUST NEVER be silently dropped. A valid
document that a structure cannot represent MUST be rejected by the reader.
Reading MUST NOT allocate in proportion to the input except from the
caller-provided arena, and arena exhaustion MUST be reported.

## Critical rule

Unsupported XSD constructs MUST cause `mxsdc` to fail.

They MUST NEVER be silently ignored.

Example:

    error: unsupported XSD construct 'xs:keyref'

## Generated code requirements

Generated code MUST:

- be deterministic
- compile as C
- be suitable for embedded systems
- avoid heap allocation where possible
- avoid POSIX
- avoid filesystem access
- avoid network access
- contain no XSD parser
- contain no unused schema information

Generation of the same XSD MUST produce byte-identical output.

## Runtime

libmxsd MUST:

- be written in portable C
- have no POSIX dependency
- have no filesystem dependency
- have no network dependency
- be usable with Zephyr
- provide structured validation errors

## Validation

The generated validator MUST detect at minimum:

- missing required elements
- unexpected elements
- incorrect element order
- occurrence violations
- missing required attributes
- unexpected attributes where applicable
- invalid primitive values
- violated restrictions

## Testing strategy

Every supported XSD construct MUST have:

1. XSD input
2. expected generated C
3. valid XML
4. invalid XML
5. host validation test
6. Zephyr validation test where applicable

Compiler tests MUST verify generated output.

Runtime tests MUST verify both valid and invalid documents.

## Security

Treat both XSD and XML as untrusted input.

The compiler MUST detect:

- invalid recursive simple types and circular type derivation
- invalid references
- integer overflow
- pathological occurrence values
- unsupported constructs

The runtime MUST protect against:

- malformed XML
- integer overflow
- excessive nesting
- excessive input size where configured

## Development process

Implement one XSD feature at a time.

For every feature:

1. add compiler tests
2. implement parsing
3. generate C representation
4. add valid XML test
5. add invalid XML test
6. run host tests
7. run sanitizers
8. run Zephyr tests
9. update support matrix

Never implement several unrelated XSD features in one iteration.
Never claim support for a construct without validation tests.
